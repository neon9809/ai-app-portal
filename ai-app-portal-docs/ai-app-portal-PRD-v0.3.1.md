## 0. 一句话定位

**AI应用门户**：把散落在各端口的自部署应用（尤其 AI 应用）收敛到一个域名下——统一入口、自动 HTTPS、登录鉴权、主题品牌、会员与 token 计费；**人从门户进来，应用经平台调用大模型**。

```
用户 ──HTTPS──▶ ai-app-portal（自动证书，监听端口）
                  ├─ 门户 UI ──▶ 应用卡片墙 / 主题 / 品牌 / 备案
                  ├─ 用户中心 ──▶ 个人信息 / 财务 / 安全 / 注销
                  ├─ 应用网关 ──▶ 路径反代 ──▶ 127.0.0.1:8001 (app A)
                  │             ──▶ 127.0.0.1:8002 (app B)   [HTTP + WS/SSE]
                  ├─ LLM 网关 ──▶ OpenAI 兼容中转 ──▶ 阿里云/智谱/火山/vLLM…
                  └─ 计费 ──▶ 会员×应用可见性 + token 额度池
```

应用本身只监听 localhost，永不直接暴露。

## 1. 背景与问题

1. **暴露困境**：自部署 AI 应用直接暴露端口 = 无 TLS、无统一鉴权、无审计。
2. **现有方案割裂**：Caddy/nginx 只有反代；homepage 类只是导航页；one-api 类只有 LLM 中转没有门户与用户体系。
3. **AI 应用开发者的真实痛点**：用提示词攒出一个 AI 应用很容易，但要给它配 **用户、支付、模型 key 管理、HTTPS** 才能运营——这正是本平台托底的部分。

## 2. 目标用户与场景

| 用户 | 场景 |
|---|---|
| 个人 / NAS 用户（飞牛为主） | 应用商店一键装，把自己跑的 AI 应用安全发布给家人朋友 |
| 小团队 / 工作室 | 对外提供会员制的 AI 小应用；收订阅费、卖 token |
| 应用开发者 | 把自己的 AI 应用接入门户，拎包入住：用户/计费/LLM 全由平台托底 |

## 3. 已定架构决策（ADR）

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| D1 | 路由模式 | **仅路径模式**，子域名不做 | 参考实现已打通路径模式（含 SPA/Dify/Next.js 上游）；子域名需 DNS/泛证书配合，门槛高收益低。坑与解法见 `app-develop` 技能 |
| D2 | WebSocket | **P0 必须支持** | AI 聊天应用依赖；fetch 模型透传不了 upgrade，需独立 `upgrade` 通道 |
| D3 | 语言 | **Node.js/TypeScript** | 复用参考实现已验证的反代/身份/安全逻辑；ACME 用 acme-client |
| D4 | 组织模型 | **单组织** | 不做多租户/白标 |
| D5 | 计费模型 | **双线：会员订阅（×应用可见性）+ token 充值（LLM 用量）** | 会员管「能用哪些应用」，token 池管「能用多少模型」；用户级计量由 passUser 身份链免费获得 |
| D6 | 品牌策略 | **OSS 版零单位指纹** | 剔除校名/校色/校徽/内置业务工具；品牌全数据化，默认纯净 |
| D7 | 分发 | **FPK + Docker 双形态，路径行为完全一致** | 业务流量都走监听端口（`service_port`），不走飞牛统一网关；网关只做桌面图标入口（见 F3） |
| D8 | 管理面板体验 | **P0 验收硬指标** | 入门用户无文档走通安装到发布，是采用与否的第一道门槛（见 E2） |

## 4. 功能需求（按功能域）

### A. 门户与身份

| # | 模块 | 说明 | 期 |
|---|---|---|---|
| A1 | **门户 UI + 主题 + 品牌** | 应用卡片墙；≥6 套内置主题（复用 fnos-dashboard 方法论）+ 强调色 + 自定义色；品牌数据化：logo/站名/主题/页脚文案/ICP+公安备案号组件（自动带链接） | M1 |
| A2 | **本地账号 + 注册** | 用户名+邮箱或手机号（唯一）+ scrypt 密码；注册入口（注册/找回密码/绑定邮箱）挂 PoW + 可选 Turnstile（后台填 key 即启用，默认 PoW 兜底）；验证码通道抽象（SMTP / 阿里云或腾讯云 SMS adapter 选一首发），6 位 5 分钟有效、同通道 60s 限 1 条 + 24h 上限、哈希存储单次有效；注册开关三档（关闭/开放/开放+邀请码，默认关闭）；同 IP 24h ≤ 5 号；废弃注册 N 天清理；首账号自动 admin | M1 |
| A3 | **MFA（TOTP + Passkey）** | TOTP（RFC 6238；±1 窗口、重放拒绝、恢复码 10 枚哈希存储）+ Passkey（`@simplewebauthn`；二次因子与无密码主登录双角色、多凭据管理）；登录状态机 `password_ok → mfa_pending → 完全会话`；敏感操作步升认证；策略：admin 强制不可关、会员默认强制、普通可选；恢复码/绑定/验证全审计 | M1 |
| A4 | **用户中心** | 个人信息（头像/昵称/绑定换绑走验证码通道）；财务（会员有效期+续订、token 余额与消耗曲线、充值、全流水）；安全（改密、MFA 管理、恢复码重生成、会话列表可踢下线、步升认证）；注销（7 天冷静期可撤回 → 数据匿名化，审计脱敏保留） | M1 |
| A5 | **OIDC 登录** | PKCE；MFA 委托 IdP；沿用参考实现 uid/kind 串号防御（(kind, uid) 联合隔离） | M2 |

### C. LLM 网关

**定位**：平台内应用要调大模型，一律经本网关中转，不直连云厂商。管理员统一维护 key、路由、计量。**网关对调用形态（Agent / 单次任务）无感**。

| # | 模块 | 说明 | 期 |
|---|---|---|---|
| C1 | **OpenAI 兼容端点** | `/v1/chat/completions`（含流式）、`/v1/models`；任意 OpenAI SDK 改 base_url + api_key 即接入 | M2 |
| C2 | **网关凭据** | 应用持网关 app-token（注册下发；passUser 场景随身份注入一并提供）；可吊销、可限额；真实上游 key 只存网关侧永不下发 | M2 |
| C3 | **上游与模型目录** | 多上游配置（阿里云/智谱/火山/本地 vLLM）；聚合统一 `/v1/models`；应用 `model` 字段选模型，网关按模型路由 | M2 |
| C4 | **路由策略** | 同模型多上游：failover（超时/5xx/限流切换）、健康检查、轮询/加权；流式断流处理 | M2 |
| C5 | **计量与限额** | 双粒度：应用级 + **用户级**（passUser 身份链归因，零成本）；配额超限 429；全调用审计（谁/哪个应用/什么模型/多少 token/耗时）。用户级计量是 D2 token 计费的数据底座 | M2 |
| C6 | **预检闸门** | 网关转发前查**本地余额缓存**（按模型倍率原子递减预估成本）；缓存判定无余额 → 直接 402，请求不出网关。缓存由 D 同步/失效（扣款、充值、手动调额三个动作都必须触发失效）。流式请求按 max_tokens/历史均值预估，**不在流中途掐断**，事后校正 | M2 |

> **C/D 边界原则：账本只有一份（C 的用量流水，append-only，只记不判）；余额只有一处（D 结算，读流水算余额）。** C 是请求路径上的记录者与预检者，D 是非请求路径上的结算者。

### D. 计费

| # | 模块 | 说明 | 期 |
|---|---|---|---|
| D1 | **会员订阅 × 应用可见性** | 免费应用全员可见；会员应用仅订户可用；等级绑定应用集合；到期降级（关会员应用、保留数据） | M3 |
| D2 | **Token 充值** | 基于 C5 用户级计量：充值进 token 额度池，按模型单价扣减（不同模型不同倍率，管理员定价）；余额不足拒付（402）；充值/消耗全流水 | M3 |
| D2a | **结算引擎（读流水）** | 异步消费 C 的用量流水 → 按定价倍率结算扣减 → 更新余额；实际消耗打穿余额（流式超长/并发在途）→ 标记**欠费态**并**主动失效 C6 预检缓存**（下一发请求在第一道闸被拦）。漏账上限 = 并发在途请求的预估成本之和（可控、非账目错误） | M3 |
| D2b | **缓存同步** | 三个动作必须通知 C 作废预检缓存：扣款（欠费态）、充值到账、管理员手动调额。单机部署用进程内事件总线即可 | M3 |
| D3 | **支付渠道抽象** | 国内（微信/支付宝）与海外（Stripe）adapter，首发选一边；充值订单对接 D2 | M3 |
| D4 | **运营面板** | 用户余额/消耗排行、应用调用热度、上游成本 vs 收入毛利 | M3 |

### G. 生态（.neon-aap 扩展体系，复用 fnos-dashboard 的 .neon-dash 方法论）

用户可上传 **`.neon-aap` 包**（ZIP：`manifest.json` + 静态 HTML 工具 **或** Python 脚本 `mod.py`）。包遵循 `app-develop` 技能定义的出入参规范（manifest 声明工具名/图标/类型/所需能力；Python 实现标准入口，出入为结构化 JSON）。

| # | 模块 | 说明 | 期 |
|---|---|---|---|
| G1 | **包格式与校验** | manifest.json 必填字段校验（名称/版本/类型 html\|python/入口/**能力声明**）；能力声明含：`capabilities`（llm/db/storage）、`network`（**出站域名白名单**，逐条列域名）、`runtime`（**按调用 invoked \| 持久服务 persistent**，persistent 需声明监听端口/路由前缀）。HTML 包 = 静态资源沙箱（iframe 沙箱属性 + CSP，禁同源 cookie）；Python 包 = 单文件 `mod.py`，依赖白名单（仅标准库 + 平台 SDK 存根）；**审核页展示全部能力声明，管理员照单审批** | M4 |
| G2 | **Python 沙箱运行时** | 隔离子进程：CPU/内存受限；**进程本身无网络**，HTTP 出口唯一通道 = 平台出站代理（逐请求对照 manifest 域名白名单放行，拒绝未声明域名——防 DNS rebinding/直连 IP 绕过）；SDK 存根：`llm.chat()`（走 C 域网关，计入调用者 token 池）、`db.*`（**每包独立 SQLite，包内完整 SQL**，跨包/平台表物理隔离，容量限额）、`storage.*`（每包独立配额空间）；出入结构化 JSON 校验；容器部署叠加 ns/cgroups。**两种运行时**：**invoked（按调用）**——每次请求新进程，跑完即毁，适合数据处理类；**persistent（持久服务）**——manifest 声明后由平台拉起长驻进程，注册路由前缀（如 `/app/<id>/` 下），提供 HTTP 服务（网页/自定义 API），平台反代纳入 B 域正常管理（限流/审计/健康检查同样生效），资源限额更严格（常驻内存上限、空闲自动回收、崩溃自动重启） | M4 |
| G3 | **可见性三态** | **私有**（仅上传者自己可用）/ **审核中**（提交给管理员）/ **公开**（管理员审核通过后对所有用户开放）；审核 = 管理面板内查看代码/试运行/一键通过或驳回（驳回带理由） | M4 |
| G4 | **生命周期与安全** | 上传 → 校验（G1）→ 私有可用；公开需审核；版本更新视为新审核；签名机制预留（fnos-dashboard 的 ed25519 信任链，官方包免审）；任意用户可举报，管理员可下架；全部事件入审计 | M4 |
| G5 | **工具运行** | HTML 工具经门户 shell（iframe）嵌入，复用 A1 卡片墙展示；Python 工具由门户提供统一执行入口（表单 → 沙箱 → 结果渲染），运行记录入审计（谁、哪个包、耗时、LLM token 消耗） | M4 |

> 生态边界（明确不做→逐步放开）：第一版不支持任意 pip 依赖、跨包调用；db/storage 为受控白名单方法而非任意读写；域名白名单写进 manifest 并随审核走（改白名单 = 重新审核）。跑通「用户造工具 → 自己用 → 审核上架」循环后再逐步扩大能力面。

## 5. 非功能需求

- **安全**：upstream 仅绑 localhost/内网；secrets 不落前端；身份头必须验签；管理界面独立凭证；安全栈（PoW/失败计数/IP 封禁倍增/CSRF Origin/scrypt/审计）全套移植。
- **性能**：WS/SSE 零缓冲透传；单机千级并发；证书热替换不断连。
- **可靠性**：upstream 健康检查与摘除；配置热更新；门户崩溃不打断已建立连接。
- **部署**：单容器 NAS 友好；支持纯门户模式（反代外置给已有 Caddy/nginx）。
- **合规**：备案号组件化；预留内容安全审查接口。
